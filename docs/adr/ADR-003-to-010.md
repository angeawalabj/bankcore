# ADR-003 — Protocol (duck typing) vs ABC pour le DIP

**Statut :** Accepté  
**Date :** 2026-02-12 (J10)

## Décision
Utiliser `typing.Protocol` pour les interfaces injectées (`ConfigProtocol`,
`AlertProtocol`) plutôt que des ABC.

## Raison
`ConfigManager` et `AlertSystem` existaient avant le DIP (J10).
Les forcer à hériter d'une nouvelle ABC aurait cassé tous les tests existants.
`Protocol` permet le duck typing structurel : toute classe avec les bonnes
méthodes satisfait le protocole, sans déclaration explicite.

## Conséquence
`FakeConfig` et `SpyAlertSystem` satisfont `ConfigProtocol`/`AlertProtocol`
sans héritage → injection dans les tests sans patching global.

## Alternative rejetée
ABC avec `ABCMeta` → nécessitait de modifier `ConfigManager` et `AlertSystem`,
cassant 200+ tests existants.

# ADR-004 — Port dans Application, Adapter dans Infrastructure

**Statut :** Accepté  
**Date :** 2026-02-16 (J12)

## Décision
`AccountRepositoryPort` est défini dans `bankcore/application/ports.py`,
**pas** dans `bankcore/infrastructure/`.

## Raison
La Clean Architecture exige que les dépendances pointent vers l'intérieur.
Si le Port était dans Infrastructure, Application dépendrait d'Infrastructure.
Le Port appartient à celui qui le **définit** (Application), pas à celui
qui l'**implémente** (Infrastructure).

## Conséquence
```
Application  → définit AccountRepositoryPort
Infrastructure → importe et implémente AccountRepositoryPort
```
`InMemoryAccountRepository` et `SQLiteAccountRepository` dépendent toutes
deux du Port défini dans Application — jamais l'inverse.

## Preuve
`test_infrastructure_imports_application_ports` vérifie programmatiquement
que la direction de dépendance est correcte.

# ADR-005 — SQLite UUID (TEXT) vs INTEGER auto-increment pour les PKs

**Statut :** Accepté  
**Date :** 2026-02-17 (J13)

## Décision
Les clés primaires de toutes les tables sont `TEXT` contenant des UUID,
générés par le Domaine Python, pas par SQLite.

## Raison
1. **Pas de fuite d'information** : `account_id=7` révèle qu'il y a ~7 comptes.
   Un UUID n'est pas devinable.
2. **Génération distribuée** : des UUID peuvent être générés par n'importe quel
   service sans coordination avec la BDD.
3. **Portabilité** : en migration vers PostgreSQL, les UUID restent valides.
4. **Le Domaine reste maître de son identité** : `AccountId.generate()` (J12)
   génère l'ID avant la persistence, pas après.

## Conséquences négatives
- Index légèrement moins performants qu'INTEGER sur SQLite
- Les UUID sont moins lisibles dans les logs

# ADR-006 — Orchestration vs Choreography pour la Saga (J23)

**Statut :** Accepté  
**Date :** 2026-03-03 (J23)

## Décision
Implémenter le Saga Pattern avec **orchestration** (SagaOrchestrator centralisé)
plutôt qu'avec **choreography** (chaque service réagit aux événements).

## Raison

**Choreography :**
```
DebitSource → publie TransferDebited
                     → ConvertCurrency écoute, publie CurrencyConverted
                                              → CreditDestination écoute...
```
Avantage : découplé. Inconvénient : le flux est invisible dans le code.
En cas de bug, il faut analyser les logs de tous les services.

**Orchestration :**
```python
saga.add_step(DebitSourceStep)
saga.add_step(ConvertCurrencyStep)
saga.add_step(CreditDestinationStep)
result = saga.execute(context)
```
Le flux complet est lisible en un coup d'œil.
La compensation est explicite et testable en isolation.

## Conséquence
`SagaOrchestrator` est un point de défaillance unique. En production,
il doit être persistent (état de la saga survit aux redémarrages).
BankCore J23 est in-memory — à compléter avec `EventSourcedSagaOrchestrator` (J21+J23).

# ADR-007 — id(consumer) vs consumer.name pour l'idempotency du MessageBus

**Statut :** Accepté (après correction de bug)  
**Date :** 2026-02-24 (J18)

## Décision
La clé d'idempotency du MessageBus est `f"{message_id}:{id(consumer)}"`,
**pas** `f"{message_id}:{consumer.name}"`.

## Raison (bug trouvé en tests)
```python
c1 = RecordingConsumer()  # name = "RecordingConsumer"
c2 = RecordingConsumer()  # name = "RecordingConsumer"

# Avec consumer.name :
key_c1 = f"{msg_id}:RecordingConsumer"  # ← COLLISION
key_c2 = f"{msg_id}:RecordingConsumer"  # ← MÊME CLÉ

# c2 voit la clé déjà dans processed_ids → skip → bug silencieux
```

```python
# Avec id(consumer) :
key_c1 = f"{msg_id}:{id(c1)}"  # ← unique par instance
key_c2 = f"{msg_id}:{id(c2)}"  # ← différent
```

## Conséquence
L'idempotency est garantie par paire (message, instance_consommateur).
Le même message peut être traité par deux instances différentes du même
type de consumer — comportement correct pour les consumers parallèles.

# ADR-008 — CircuitBreakerClient catch-all vs re-raise

**Statut :** Accepté  
**Date :** 2026-03-04 (J24)

## Décision
`CircuitBreakerClient._call()` capture **toutes les exceptions** du service
et retourne `ServiceResponse(503, ...)` au lieu de les propager.

## Raison
`TransactionMicroservice` dépend de `ServiceClient` et s'attend à toujours
recevoir un `ServiceResponse` — jamais une exception.
Si `AccountService` plante avec `RuntimeError("Network error")`,
`TransactionMicroservice` ne doit pas planter par ricochet.

```python
# Avant fix : RuntimeError propagée → TransactionService crash
# Après fix : RuntimeError → ServiceResponse(503) → TransactionService continue
```

## Conséquence
Le Circuit Breaker garantit l'isolation des pannes. `TransactionService` reçoit
toujours un objet exploitable, même en cas de panne complète d'AccountService.

# ADR-009 — Event Sourcing : interest_rate non persisté comme événement

**Statut :** Accepted (dette technique documentée)  
**Date :** 2026-03-01 (J21)

## Contexte
`AccountAggregate.apply_interest()` nécessite `self._interest_rate > 0`.
Lors de la reconstruction depuis les événements (`from_events()`),
`_interest_rate` n'est pas restauré car `AccountOpened` ne le contient pas.

## Décision court terme
Restaurer `_interest_rate` implicitement dans `_apply(AccountOpened)` en
fonction de `account_type` :
```python
if event.account_type == "savings":
    self._interest_rate = 0.025
```

## Dette technique
En production, `_interest_rate` devrait être un événement de domaine explicite
(`InterestRateSet`) ou inclus dans `AccountOpened`. Le taux peut changer au cours
de la vie d'un compte — le traitement actuel ne le supporte pas.

## Plan de résolution (J30+)
```python
@dataclass(frozen=True)
class InterestRateSet(DomainEvent):
    new_rate: float
    effective_from: datetime
```

# ADR-010 — Séparation ConfigManager / SecretsProvider

**Statut :** Accepté  
**Date :** 2026-03-06 (J28)

## Décision
`ConfigManager` (J01) gère les **paramètres non-sensibles**.
`SecretsProvider` (J28) gère les **valeurs sensibles**.

La ligne de démarcation :
- ConfigManager : `limits.max_transfer_amount`, `environment`, `database_url`
- SecretsProvider : clé HMAC, mot de passe BDD, JWT signing key

## Raison
Les valeurs de ConfigManager peuvent apparaître dans les logs sans risque.
Les valeurs de SecretsProvider ne doivent **jamais** apparaître dans les logs,
les traces, ou les crashdumps.

Séparer les deux permet d'appliquer des politiques différentes :
- ConfigManager : modifiable à chaud, versionnable dans git
- SecretsProvider : rotation possible, audit d'accès, HSM en production

## Conséquence
```python
# Non-sensible → ConfigManager
max_transfer = config.get("limits.max_transfer_amount")

# Sensible → SecretsProvider
hmac_key = secrets.get(SecretKeys.AUDIT_HMAC_KEY)
audit_log = ImmutableAuditLog(secret_key=hmac_key)
```

Le code de production ne mélange jamais les deux sources.
